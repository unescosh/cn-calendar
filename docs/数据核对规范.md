# 数据核对规范 v1

定稿日期：2026-11-09
适用：本地计算 + 联网核对的完整链路。

## 一、原则：本地是基础，联网是校验

日历最重要的是精确，而精确不能靠"联网拿一份数据直接覆盖"获得。分层处理：

| 层 | 本地是否有权威计算 | 联网的角色 |
|---|---|---|
| L1 固定公历纪念日 | 有（法律/国务院规定，静态表） | **仅核对存在性**，不得改写 |
| L2 规则型纪念日 | 有（本地 nth-weekday / 节气算法） | **仅核对结果**，不得改写 |
| L3 农历、节气、干支 | 有（预生成静态表 + 区间定位） | **仅核对结果**，不得改写 |
| L4 年度调休 | 无（国务院每年发布，无法推算） | **允许更新**，但更新前先比对差异 |

一句话：**联网数据无权覆盖本地已通过测试锁死的计算结果**。
只有 L4 属于"本地算不出来、必须外部输入"，才允许写入缓存；即便如此，也要先出差异报告。

## 二、核对项

1. **日期与星期基准**
   - 取多个 HTTP 响应的 `Date` 头（RFC 7231 IMF-fixdate，如 `Mon, 09 Nov 2026 01:31:40 GMT`），
     解析出 UTC 日期与星期。任何 HTTP 服务器都会返回该头，不需要专用时间 API、不需要信任第三方数据内容。
   - 三方比对：远端 `Date` 头 ↔ 本机 UTC 日期 ↔ `cn_cal_cli day <今天>` 的 `weekday` 字段。
   - 任一不符 → `weekday_mismatch` / `clock_skew`，报告差异，不自动改本地时间。
2. **本地算法自洽**
   - `cn_cal_cli verify weekday`：逐日验证 `days_from_civil` / `civil_from_days` 往返一致，
     且星期按 0→6 循环连续，覆盖 2020–2050。
   - 这是"日期、星期必须准确"的离线兜底，断网也要跑。
3. **L4 快照与上游一致性**
   - 拉 `holiday-cn/{year}.json`，与 `data/holiday-{year}.json` 及运行时缓存逐条比对
     （日期 + `isOffDay`），差异分类为 `added` / `missing` / `changed`。
   - 一致才允许把上游写入缓存；有差异时仍写入（因为上游是唯一权威来源）但**必须出报告**。
4. **节日抽样核对**
   - 四个国家级纪念日（9/3、9/30、12/4、12/13）在任意年份都必须出现在本地 `labels` 中。
   - 上游每个 `isOffDay=true` 的法定假日日期，本地 `day()` 必须判定 `rest=true`。
   - 上游每个 `isOffDay=false` 的补班日，本地 `day()` 必须判定 `makeup=true && workday=true`。
   - 这条能同时抓出：快照过期、合并优先级写反、缓存覆盖失效三类问题。
5. **双实现逐日交叉核对**
   - `node tools/cross_check_lunar.js <cn_cal_cli>`：用 lunar-javascript 逐日独立计算
     2020-01-25～2050-12-31 的农历月/日/闰标记/文本、节气、干支、生肖，
     与 Rust 核心 `month` 输出比对 7 个字段 × 11299 天。
   - 目的是验证「查表结果与权威算法一致」，而不只是「表本身自洽」——
     能抓出区间定位、闰月边界、跨年归档、节气按年归档错位等生成器校验发现不了的问题。
   - 本机实跑 79093 次比对零差异；已固化进 CI 的 `data-and-core` job。

## 三、报告契约

写入 `<缓存目录>/verify-report.json`（界面读取展示），同时可由 CI 采集：

```json
{
  "checked_at": "2026-11-09T01:31:40+00:00",
  "mode": "online-verify",
  "status": "consistent | differences | offline",
  "sources": ["..."],
  "checks": [
    { "id": "http-date-weekday", "status": "ok", "detail": "..." },
    { "id": "weekday-continuity", "status": "ok", "detail": "..." },
    { "id": "holiday-2026", "status": "ok", "detail": "..." },
    { "id": "festival-sampling", "status": "ok", "detail": "..." }
  ],
  "differences": [
    { "id": "weekday_mismatch", "date": "2026-11-09", "detail": "..." }
  ],
  "notes": ["本地 L1/L2/L3 未被联网数据改写"]
}
```

`status`：
- `consistent`：全部一致
- `differences`：发现差异，需人工确认（CI 退出码 2，界面显示提示）
- `offline`：网络不可用，跳过在线项，仅保留本地算法自洽检查，**不算失败**

差异 ID：`clock_skew`、`weekday_mismatch`、`holiday_added`、`holiday_missing`、
`holiday_changed`、`festival_missing`、`priority_mismatch`、`cli_error`。

## 四、失败与降级

- 任一 HTTP 源超时/不可达 → 换下一个源；全部失败 → `offline`，退出码 0，绝不弹窗。
- 上游 JSON 校验失败（年份不符、日期跨年、`days` 为空）→ 丢弃该份数据，保留本地快照，记 `holiday_changed`。
- 核对工具本身出错 → 记 `cli_error`，不修改任何本地数据。
- **绝不**因为联网核对结果去改写 `data/` 下的静态数据；那是源码，改动必须走测试与版本控制。

## 五、运行时接线

- 界面启动时 `unawaited(VerifyService().run())`，不 await、不阻塞首屏。
- `UpdateService` 与 `VerifyService` 共用 `CN_CAL_HOLIDAY_DIR` 缓存目录，
  `cn_cal_cli` 启动时读取该目录覆盖 L4（校验失败静默回退内置快照）。
- 命令行/CI 用 `python tools/verify_online.py`，逻辑与界面一致，报告格式相同。

## 六、运行时校准频率（2026-11-09 用户追加）

用户明确：软件常驻后台，节假日与纪念日大多是固定或提前定好的，
更新不宜频繁，「定期校准」即可，但精确性必须保证。据此把**频率**与**精度**拆开处理：

| 动作 | 频率 | 联网 | 精确性来源 |
|---|---|---|---|
| 本地日期/星期/农历/节气计算 | 每次启动、每次取月 | 否 | Rust 核心，34 个测试 + 11323 天连续 + 79093 次双实现比对锁死 |
| HTTP `Date` 权威日期/星期基准核对 | 默认 **7 天**一轮 | 是 | 多源响应头，不信任第三方内容 |
| 11323 天星期连续性 + L4 差异报告 | 默认 **7 天**一轮 | 否（本地）/ 比对缓存 | 报告契约见第三节 |
| L4 年度调休上游同步 | **11～1 月每天**；其余月份 **30 天** | 是 | 国务院每年发布一次 |
| 上次为 offline 后的重试 | **6 小时** | 是 | 联网恢复后尽快补基准 |
| 跨年 / 系统时钟回拨 | 立即强制重跑 | 是 | 内置 L4 快照按年组织 |
| 用户点「立即校准」 | 随时 | 是 | 跳过节流，走完整核对 |

不变的四条底线：

1. L1/L2/L3 永远不被联网数据改写，联网只核对存在性与结果。
2. 差异一律写进 `verify-report.json` 并在界面显示，不静默吞掉；
   `differences` 状态在缓存命中时照样显示。
3. L4 一旦写入新文件，界面立即清空月份缓存重取当月，不会显示过期调休。
4. **CI 侧口径不变**：每次 push 仍跑全量数据校验、34 个 Rust 测试、
   11323 天星期核对、79093 次双实现逐日比对与联网核对。
   运行时降频只是减少重复劳动，不削弱开发期的完整验证。

界面上「数据核对」图标 →「立即校准」是手动兜底：用户想随时确认精度时，
不必等 7 天，也不用重启软件。
