# 资源占用规范（轻量运行与定期校准）

> 2026-11-09 新增需求：两台办公电脑配置不高，软件运行占用系统资源要少。
> 同日追加：软件常驻后台，节假日与纪念日大多是固定或提前定好的，
> 更新不宜频繁，只需定期校准（但必须保证精准）。
> 本文件给出量化口径、实测依据、设计约束与验收方式。

## 目标机器

| 机器 | CPU | 内存 | 特点 |
|---|---|---|---|
| Windows 10 | Intel i3-8100（4 核 4 线程，3.6GHz，2018） | 16 GB | 单线程尚可，核心数少 |
| 统信 UOS 20 | 海光 C86-3G 3350（8 核 16 线程，3.0–3.3GHz，65W，Zen1 12nm） | 16 GB | 多核够用，**单线程偏弱**（PassMark 单线程 1720 / 多核 11739） |

两台都是老平台，但 **16 GB 内存并不紧张**。瓶颈是启动峰值、进程创建与后台空转，
不是内存容量。优化方向据此确定：削峰 + 降频，而不是压缩常驻内存。

## 量化口径与评估

| 指标 | 目标 | 改动前 | 改动后 | 判定 |
|---|---|---|---|---|
| 常驻内存（Release、空闲） | ≤ 150 MB | Flutter 桌面公开基线约 100–250 MB | **UOS 实机 81–86 MB** | 达标（实机） |
| 空闲 CPU | ≤ 1%，无周期轮询、无常驻动画 | UI 静态、无持续动画；但启动后台任务偏多 | UI 静态；UOS 静止约 **1.3%** | 接近达标 |
| 启动时 CLI 进程数（日常启动） | ≤ 2 | 5–7 次（month / day / verify weekday / 每年 verify holiday） | **1 次**（只取当月；校准报告命中缓存，0 次核对进程） | 达标 |
| 启动时 CLI 进程数（首次 / 校准到期） | 允许一次性全量核对 | 5–7 次 | 4–5 次（完整精确性核对，按用户要求不删减） | 一次性 |
| 启动后台网络请求 | 定期校准，不是每次启动都发 | 每次启动最多 6 个（2 个 HEAD + 2 年 × 2 源） | 命中缓存 **0 个**；首次最多 6 个 | 达标 |
| 联网核对 / 全量星期核对 | 默认 7 天一轮 | 每次启动都跑 11323 天 | 7 天一轮；跨年、时钟回拨、用户点「立即校准」时强制重跑 | 达标 |
| L4 年度调休同步 | 按发布季分频 | 每次启动 2 年 × 2 源 | 11～1 月每天，其余月份 30 天；失败也节流 | 达标 |
| 磁盘缓存 | < 1 MB | 内置数据约 100 KB + 少量 JSON | 多 2 个时间戳/报告小文件 | 达标 |

**结论：改动前不完全满足，已按需求修改软件；不必更换 UI 技术栈。**
Flutter 桌面常驻内存比原生 GTK（10–40 MB）高，但对 16 GB 机器只占 0.6%–1.5%；
换成 Qt / 原生会推翻已完成的双端构建、CI 与 UOS glibc 2.28 兼容工作，代价与收益不匹配。
UOS 实机初测已量到 81–86 MB 与 1.3% 空闲 CPU，启动峰值与后台空转两项已落地；
**71 秒初测不等于长期稳定**，24 小时内存漂移曲线仍待量测，未量测前不得宣告 P2 常驻形态达标。

|---|---|

## 设计约束（已落地）

1. **定期校准、后台降频**（用户 2026-11-09 追加）：`ResourcePolicy` 用
   `verify-report.json` 的 `checked_at` 与 `last-sync.txt` 时间戳做节流。
   - 联网权威日期核对 + 11323 天星期连续性 + L4 差异报告：默认 **7 天**一轮；
   - L4 年度调休同步：**11～1 月每天**，其余月份 **30 天**（`syncIntervalFor`）；
   - `offline` 状态的报告 **6 小时**后重试（`intervalFor`）；
   - 跨年（内置 L4 快照按年组织）或系统时钟回拨：强制重跑（`needsRecheck`）；
   - 用户点核对图标 →「立即校准」：`run(force: true)` 跳过节流走完整核对；
   - 命中缓存时**零网络请求、零 CLI 进程**，首次启动仍做完整核对。
2. **本地计算不降频**：日期、星期、农历、节气每次启动照常由 Rust 核心算，
   零网络、零额外进程。精确性来自已锁死的本地算法，不依赖联网频率。
3. **月份内存复用**：`MonthCache` 最多缓存 12 个月，翻回看过的月份不再启动进程。
4. **失败也要节流**：同步无论成功失败都写标记。离线时不写会导致每次启动反复
   发起 8 秒超时的请求，反而更耗资源。
5. **精确性不被削弱**（用户明确要求）：
   - 节流只跳过「重复计算与重复联网」，不改写任何 L1/L2/L3 数据；
   - 复用的是已生成的报告，`differences` 状态仍会显示，差异不会被静默吞掉；
   - `UpdateService` 一旦写入新的 L4 文件就返回 `dataChanged=true`，
     `main.dart` 收到后调用 `_bridge.clearCache()` 并重取当月数据，
     **保证不会显示过期的调休安排**；`_loadSeq` 递增序号防止并发刷新时旧结果覆盖新结果。
6. **不做的事**：不做周期轮询、不做常驻动画、不做后台定时器、不常驻第二个进程、
   不引入图片/字体等大资源、不上报遥测。
7. **缓存只在内存**：`MonthCache` 不落盘。CLI 单次约 27 ms，为它引入磁盘
   序列化与失效管理反而更重；重启后重新取当月一次即可。
8. **切月动画只做整屏推入，不做交叉淡入**（用户 2026-11-10 第六轮修正）：
   第四轮「12% 小位移 + `FadeTransition` 交叉淡入」在双端实机出现文字残影，
   根因是新旧两页半透明叠加、格子底色也是半透明（`0x14...`），两层中文重影；
   第五轮一度整体回退到无动画，用户明确要求「调整和优化滚动动画」，
   故第六轮**保留动画但改掉结构**，让它物理上不可能出现两层文字：
   - 位移 **1.0 整屏**（不是 0.12），新页与旧页首尾衔接、任意时刻不重叠；
   - **完全去掉 `FadeTransition` / 任何透明度动画**；
   - 每页 `DecoratedBox` 垫不透明底，`ClipRect` 裁掉滑出可见区的那一页，
     `RepaintBoundary` 独立重绘，避免脏矩形残留；
   - `switchInCurve` / `switchOutCurve` 都用中心对称的 `Curves.easeInOut`，
     否则入/出两页速度不同会露出底色缝隙；**禁止改回 `easeOutCubic`**。
   仍是一次性 220ms：结束后 controller 停在完成态、Ticker 静默，
   静止时无帧回调、无循环动画，不违反第 6 条。
   `widget_test.dart` 有源码级断言锁死上述结构。

## P2 挂件 / 托盘阶段的硬约束

挂件是**长期常驻**形态，比一次性窗口更容易累积资源占用，必须遵守：

- 窗口隐藏 / 最小化时暂停渲染与刷新，不保持 vsync 回调；
- 只在「日期跨天」「用户主动翻开月历」「L4 数据更新」三种情况下重绘；
- 不使用无限循环动画（包括加载指示器动画完成后必须停止）；
- 托盘图标用系统托盘 API，不用 Flutter 窗口模拟；
- **开机自启**：Win10 走 `HKCU\...\Run`，UOS 走 `~/.config/autostart/*.desktop`；
  挂件与主窗口共用一个进程，不额外拉起常驻子进程，且必须提供显式开关；
- 常驻进程只有一个（P3 的 FFI 替换 CLI 桥接正是为此）；
- 上线前必须在两台目标机上各连续运行 24 小时，记录空闲内存/CPU 曲线，
  确认没有无界增长（常驻应用真正的风险是内存漂移，不是启动基线）。

### P2 第 1 步的资源口径（2026-11-10 16:40，Win10 托盘 + 时间接管）

这一步把「一次性窗口」变成「常驻」，逐条对齐上面的硬约束：

| 约束 | 本步做法 |
|---|---|
| 常驻进程只有一个 | 托盘、鼠标钩子、单实例检测全在主 `cn_calendar.exe` 内；只多一个托盘线程，不拉起任何子进程 |
| 隐藏时暂停刷新 | X 按钮改为 `ShowWindow(SW_HIDE)`；Dart 侧未新增任何定时器或 vsync 回调 |
| 无后台轮询 / 定时器 | 钩子只在真实鼠标事件时回调；托盘线程阻塞在 `GetMessage`；没有 `SetTimer`、没有周期联网 |
| 不新增联网 | `ResourcePolicy` 的 7 天核对、分季同步、offline 6 小时口径一字未改 |
| 显式开关 | 托盘菜单可关「接管任务栏时间」与「开机自启」；`HKCU\Software\CNCalendar\HookTaskbarClock` |
| 24 小时曲线 | **仍未量**，是宣告 P2 完成的前置；本步只做到不引入新的空转来源 |

钩子回调的额外开销只发生在用户点击鼠标的瞬间，且只做
`WindowFromPoint` + 最多 5 层 `GetClassNameW`；静止时该线程阻塞在
`GetMessage`，不消耗 CPU。真正的风险仍是常驻内存漂移，
**只能靠 Win10 连续 24 小时实测量结论**，本机无 GUI 采样数据、不编造。
实现细节见 `docs/P2第一步_Win10托盘与时间接管.md`。

### P2 第 2 步的资源口径（2026-11-11 15:17，Win10 桌面挂件）

| 约束 | 本步做法 |
|---|---|
| 常驻进程只有一个 | 挂件窗口由主进程在 `wWinMain` 线程创建，复用现有 `GetMessage` 循环；托盘线程仍是唯一额外线程 |
| 不新增线程 / 定时器 | 原生层没有 `CreateThread`、没有 `SetTimer`、没有轮询；静止时窗口不收 `WM_PAINT` |
| 不新增联网 | 挂件数据来自已缓存的当月 `DayInfo`，命中 `MonthCache` 不启动 CLI 进程 |
| 只画一次 | 启动 / 回到当月 / L4 更新 / 主题切换 / 跨天才重绘；翻到别的月份不重画 |
| 日期哨兵 | Dart 每 30 分钟只比一次「年-月-日」字符串，日期没变零动作；变化才重绘一次。这是本步唯一新增的周期性动作，不联网、不重绘主窗口、一天最多一次实际重绘 |
| 内存增量 | 一张 448×424×4 ≈ 763 KB 的 32bpp DIB，刷新时重建、旧的立即释放；不常驻大图 |
| 显式开关 | 托盘菜单「桌面挂件」写 `HKCU\Software\CNCalendar\WidgetEnabled`，默认开；关掉后窗口 `SW_HIDE` 且不再贴图 |
| 静默降级 | 窗口注册失败 / 位图缺失 / FFI 失败一律不阻塞主界面，启动瞬间全透明不留黑块 |

**口径更新说明**：第 1 步写的是「无后台定时器」，指原生侧不引入 `SetTimer`
轮询；第 2 步 Dart 侧新增的这个哨兵同样不是轮询——它只做一次字符串比较，
不联网、不读文件、不绘制，只有跨天才触发一次离屏绘制。跨月若不刷新，
挂件会停在上个月的格子上，与「日历最重要的是精确」冲突，所以这个低频
哨兵不能省。24 小时漂移曲线仍是宣告 P2 完成的前置。
实现细节见 `docs/P2第二步_Win10桌面挂件.md`。

## 验收方式

- Dart 层：`app/test/widget_test.dart` 共 **33 个测试**，覆盖配色分类优先级、
  7 天核对间隔、按发布季分频、offline 重试、跨年与时钟回拨强制重跑、
  标记读写（含损坏文件）、缓存淘汰/清空、命中缓存不启动 CLI 进程、
  整屏推入防残影、Win10 UTF-8 契约、P2 补丁文件与 CI 接入，以及
  P2 第 2 步挂件的位图 / 消息契约、发布时机、原生置底分层与无定时器断言。
  CI `flutter-analyze` 的 `flutter test` 步骤自动跑；本机无 Flutter/Dart，
  **结论只认 CI run**（run #14 已 30/30 全绿；第 2 步新增 3 个待下一轮复核）。
- Rust 层：CLI 单次调用耗时实测见上表，作为回归基线；本轮未改 Rust 核心，
  37 个既有测试与 11323 天星期核对仍然有效。
- 双端实机：UOS 20 已有 71 秒初测（见上）；Win10 P2 第 1 步已完成交互验收
  与退出后进程数核验（0 个 `cn_calendar.exe` / 0 个 `cn_cal_cli.exe` 残留），
  **但 GUI 资源采样与连续 24 小时漂移仍未测**；等常驻形态稳定后，
  用任务管理器 / `top` 连续量测再下最终结论，不编造数据。
